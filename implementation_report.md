# Аналіз та вдосконалення процесу розгортання інфраструктури (DevOps)

Цей розділ описує технічну реалізацію інфраструктури, використання контейнеризації та організацію пайплайнів CI/CD, а також містить аналіз усунутих недоліків попередньої конфігурації.

## 1. Конфігурація інфраструктури (Infrastructure)

**Недоліки попереднього підходу:**
Підготовка інфраструктури виконувалася шляхом ручного створення ресурсу віртуальної машини (VM) та конфігурації мережі через портал хмарного провайдера. Використовувалася автентифікація на основі статичних паролів.

**Аналіз проблем:**
Ручне налаштування унеможливлює точне відтворення середовища, ускладнює аудит змін та збільшує ймовірність конфігураційних помилок. Використання статичних паролів створює вразливість для атак типу brute-force.

**Обґрунтування впровадженого рішення:**
Застосовано принципи Infrastructure as Code (IaC) із використанням інструмента Terraform. Це забезпечує ідемпотентність процесу: інфраструктура розгортається передбачувано і чітко відповідає декларативному коду. Для доступу до віртуальної машини реалізовано SSH-автентифікацію на основі криптографічних ключів. Автоматизовано застосування правил Network Security Group (NSG) для обмеження зовнішнього доступу виключно визначеними портами (22 та 80).

## 2. Безпека середовищ та ізоляція сервісів (Security & Docker)

**Недоліки попереднього підходу:**
Запуск Docker-контейнерів здійснювався від імені суперкористувача (root). Механізми зберігання даних (PostgreSQL та Redis) мали відкриті порти, доступні з публічної мережі.

**Аналіз проблем:**
Виконання процесів від імені root порушує стандарти безпеки: у разі компрометації застосунку зловмисник отримує підвищені привілеї всередині контейнера. Відкриті порти баз даних є вектором для мережевих атак.

**Обґрунтування впровадженого рішення:**
Впроваджено принцип найменших привілеїв (least privilege): створення та інкапсуляція процесу ізольованим непривілейованим користувачем (у директиві `USER` конфігурації `Dockerfile`). Реалізовано мережеву ізоляцію: бази даних і системи кешування комунікують виключно у внутрішній підмережі (Docker bridge network). Зовнішній доступ закрито. Секрети не зберігаються у коді — їхнє впровадження здійснюється системними змінними середовища через механізм GitHub Secrets алгоритмами CI/CD.

## 3. Процес збирання та розгортання (CI/CD)

**Недоліки попереднього підходу:**
Побудова Docker-образів відбувалася безпосередньо на продуктовому сервері. Робочий процес оновлення складався з ручного копіювання файлів та виконання команд напряму у консолі сервера.

**Аналіз проблем:**
Процес компіляції та пакування образів потребує суттєвих апаратних ресурсів (CPU, RAM). Його виконання паралельно з активною роботою застосунку здатне призвести до ресурсного голодування (наприклад, зупинки процесу системою Out Of Memory Killer). Ручні дії під час розгортання порушують принципи відмовостійкості.

**Обґрунтування впровадженого рішення:**
Реалізовано строге розмежування етапів збирання та розгортання. Процес перенесено на ізольовані сервери (GitHub Actions Runners). Після збирання готовий артефакт публікується у зовнішній реєстр — GitHub Container Registry (GHCR). Доставка коду відбувається автоматично: скрипт оновлює контейнери за допомогою команди `docker compose up -d` без попереднього видалення існуючого середовища, що дозволяє уникнути непотрібного руйнування загального стану та забезпечує контрольований цикл переходу на нову версію образу. Усі етапи автоматизації розроблені з урахуванням концепції ідемпотентності.

## 4. Надійність та стабільність роботи (Reliability)

**Недоліки попереднього підходу:**
Сервіси запускалися одночасно без перевірки статусу суміжних компонентів. Застосунок намагався виконати запит до СУБД під час її завантаження.

**Аналіз проблем:**
Неконтрольований порядок ініціалізації спричиняє стан "перегонів" (Race conditions). Це ініціює помилки підключення, що призводить до перезавантажень контейнера в циклі (CrashLoop) системним демоном Docker.

**Обґрунтування впровадженого рішення:**
Реалізовано дворівневий підхід до стабілізації запуску. На інфраструктурному рівні використано директиви визначення залежностей (`depends_on`) у поєднанні з механізмом `healthchecks`, гарантуючи, що контейнер вебзастосунку стартує виключно після готовності PostgreSQL приймати з'єднання. На рівні бізнес-логіки обробки бази даних впроваджено гнучкий алгоритм `retry/backoff` для підключення під час старту застосунку, який створює періодичні повторні підключення. Це підвищує системну надійність у разі короткочасних мережевих збоїв.

## 5. Обмеження системи (Limitations)

Запропонована архітектура покриває потреби дипломного проєкту, проте має наступні інженерні обмеження:
- **Апаратні обмеження:** Інфраструктура спирається на єдину віртуальну машину (single VM).
- **Висока доступність (HA):** Відсутня кластеризація та резервування обчислювальних вузлів на рівні кластера або хмарних зон.
- **Масштабованість:** Архітектурою не передбачено механізмів автоматичного горизонтального або вертикального масштабування (Autoscaling) у періоди підвищеного навантаження.
- **СУБД:** Використовується локально розгорнута СУБД у середовищі Docker, а не керовані відмовостійкі хмарні сервіси (managed DB).

## 6. Перспективи розвитку (Future Improvements)

З метою еволюції системи в напрямку парадигм Enterprise-середовищ, доцільним є впровадження наступних технологій:
- Перенесення оркестрації інфраструктури контейнерів до **Kubernetes** (використання Azure Kubernetes Service - AKS).
- Міграція баз даних та кешування на керовані хмарні сервіси (**Azure Database for PostgreSQL**, **Azure Cache for Redis**), що делегують створення резервних копій та відмовостійкі реплікації інфраструктурі хмарного провайдера.
- Інтеграція систем комплексного моніторингу та метрик обробки запитів на базі інструментів **Prometheus, Grafana** та платформи **Azure Monitor**.
- Впровадження контурів автоматичного тестування: проходження юніт- та інтеграційних тестів (на базі **pytest**) за допомогою CI-пайплайнів з умовою блокування розгортання в разі непроходження.

## 7. Інструкція з розгортання (Runbook)

**Крок 1: Ініціалізація інфраструктури**
1. Згенерувати SSH-ключ для доступу: `ssh-keygen -t rsa -b 4096 -f ./id_rsa`
2. Переміститися до каталогу конфігурацій: `cd terraform/`
3. Виконати ініціалізацію Terraform: `terraform init`
4. Застосувати зміни для конфігурації Azure: `terraform apply -auto-approve -var="ssh_public_key=$(cat ../id_rsa.pub)"`
5. Зберегти виведену IP-адресу віртуальної машини з блоку `Outputs`.

**Крок 2: Конфігурація GitHub Actions секретів**
У репозиторії налаштувати параметри `Settings > Secrets and variables > Actions`, додавши `Repository secrets`:
- `VM_HOST` (IP-адреса, отримана на кроці 1)
- `VM_USER` (ім'я користувача, наприклад: `azureuser`)
- `VM_SSH_KEY` (приватний ключ із файлу `id_rsa`)
- `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` (облікові дані для доступу).

**Крок 3: Активація процесів CI/CD**
Виконати злиття нового коду у головну гілку розробки (відправити зміни: `git push origin main`). GitHub Actions автоматично перейде до виконання збирання образів, публікації їх у GHCR та оновлення продуктового середовища.
